# 组织信息来源与 HRM 部门/员工同步设计

## 1. 意图

ss-template 是公司内部小型 Spring Boot 项目的模板。公司组织数据（分部、部门、员工）当前来自泛微 OA 的 HRM WebService，dev-bench 已在内网跑通对接。本次把这套对接迁入模板，并为以后接入其他组织来源预留替换点：

- 以 dev-bench 的实现为蓝本，把 HRM 协议客户端做成 `ruoyi-common-hrm` 模块；
- 按 dev-bench 方式扩展 `sys_dept`、`sys_user`，两边表结构保持一致；
- 把「从外部拿组织数据」抽象成接口，HRM 是其中一个实现；同步规则只写一份，与来源无关；
- 配置项选择组织信息来源，默认 `hrm`，可配置为 `none` 不启用。

当前在公司外网，无法调用 HRM WebService，也无法访问 dev-bench 的远程只读接口。凡是无法验证的协议细节，**最大程度照搬 dev-bench**——它已在内网验证过。

## 3. 目标、非目标、反目标

### 目标

1. 新增 `ruoyi-common-hrm`：HRM SOAP 只读客户端 + 4 个只读联调接口。
2. `sys_dept` 增加 10 列 + 2 个索引，`sys_user` 增加 7 列 + 1 个索引，定义与 dev-bench 完全一致。
3. 部门绑定校验、部门子树同步、员工同步三处只依赖「组织信息来源」接口，不直接依赖 HRM 客户端。
4. 配置 `org-sync.source`：`hrm`（默认）或 `none`。
5. 前端部门页、用户页加同步按钮、结果展示及部门 HRM 字段。

### 非目标

- 定时同步、批量同步、增量同步；
- 岗位同步、角色自动分配、向 HRM 写数据；
- HRM 未返回时自动删除或停用本地数据；
- 除 MySQL 外其他数据库脚本（Oracle、PG、SQLServer 不改，文档注明）；
- 实现第二个来源（只预留接口，不写示例实现）；
- 现有数据库的增量迁移脚本（`script/sql` 只做新库初始化，见 AGENTS.md）。

### 反目标（技术上能跑也算失败）

- 同步规则按来源复制成多份；
- `none` 模式下应用启动失败、读取或校验 HRM 配置，或者本地部门/用户的正常增删改受影响；
- 来源抽象泄漏 HRM 细节：通用层出现 `_canceled`、`lastChangdate`、`status=1` 之类字面量；
- 为抽象新增依赖、框架、服务或数据库表；
- 日志或返回结果包含手机号、邮箱、证件号等人员信息，或包含 OA 原始响应正文；
- 把白名单 `client-ip`、令牌、凭据等部署机相关或敏感配置写进模板（OA 接口地址按第 5 节写入，属于用户确认的例外）；
- 默认 `hrm` 模式下，HRM 不可达或未配置 `client-ip` 时无法新建普通本地部门。

- **`ruoyi-system`**：pom 增加 `ruoyi-common-hrm` 依赖；`ruoyi-admin` 通过 system 间接引入，不需要再加。
- 同步 `AGENTS.md` 的目录导航、配置说明；`script/check-template.ps1` 如有模块清单校验，确认新模块不会被误报。

## 6. 组织信息来源抽象

### 6.1 接口

在 `ruoyi-system` 中定义（包名由构建者按附近代码决定，建议 `org.dromara.system.service` 放接口、`domain.sync` 放模型）：

```java
/** 组织信息来源：只读获取外部分部、部门和员工，转换为中性模型。 */
public interface OrgSyncSource {
    /** 来源标识，与 org-sync.source 取值一致。 */
    String source();
    /** 查询全部分部。 */
    List<OrgSubcompany> listSubcompanies();
    /** 查询一个分部下完整的扁平部门列表；外部返回“无结果/无权限”时抛业务异常，不能返回空列表冒充成功。 */
    OrgDepartmentSnapshot listDepartments(String subcompanyId);
    /** 查询一个部门的员工；外部返回 null 结果时按“该部门无人员”处理（沿用 dev-bench）。 */
    List<OrgEmployee> listEmployees(String departmentId);
}
```

- 方法粒度对应 dev-bench 中 `HrmClient` 的 3 个调用点：`getHrmSubcompanyInfo`、`getHrmDepartmentInfo(分部)`、`getHrmUserInfo(departmentId)`。
- 不暴露岗位查询，同步用不到。

### 6.2 中性模型

字段对应 dev-bench 的 `DeptHrmSnapshot.Node` 和 `UserHrmRecord`，但状态改为通用语义，同时保留原值用于入库：

| 模型 | 字段 |
| --- | --- |
| `OrgSubcompany` | `id`、`parentId`（顶层为 `"0"`）、`fullName`、`code`、`disabled`、`rawStatus`、`lastChangeTime` |
| `OrgDepartment` | `id`、`subcompanyId`、`parentId`（分部下顶层为 `"0"`）、`name`、`fullName`、`code`、`orderNum`、`disabled`、`rawStatus`、`lastChangeTime` |
| `OrgDepartmentSnapshot` | `subcompanyId`、`departments`（父先子后），保留 dev-bench 的 `descendants(id)` |
| `OrgEmployee` | `id`、`workcode`、`loginId`、`name`、`gender`（已转换为本地 `0/1/2`）、`email`、`mobile`、`active`、`rawStatus`、`departmentId`、`subcompanyId`、`lastChangeDate` |

各字段语义和合法性要求：

- `rawStatus` 是来源原值，写入 `hrm_canceled` 或 `hrm_status`；`disabled`、`active` 是通用层唯一允许用于判断的字段。
- 名称取值规则（例如 `_shortname` 为空时取 `_fullname`）属于来源细节，在适配层完成；通用层只校验长度。
- 字符串统一去除首尾空白，空串转为 `null`；不过 dev-bench 中需要区分「空串 / null」的地方（例如 `hrm_canceled` 保留空串）由适配层负责保真，通用层原样写入。

### 6.3 HRM 实现（`HrmOrgSyncSource`）

- 放在 `ruoyi-system`，带 `@ConditionalOnProperty(org-sync.source=hrm)`，内部注入 `HrmClient`。
- 搬入 dev-bench `DeptHrmSnapshotParser`、`UserHrmRecordParser` 中与 HRM 格式相关的逻辑：
  - 字段名带 `_` 前缀；
  - `lastChangdate` 拼写；
  - `_canceled` 只接受 `1`、`0`、空串：`1` 为停用，`0` 和空串为正常，其他值报错；
  - `status=1` 为在职；
  - 性别 `男→0`、`女→1`、其他→`2`；
  - 时间格式分别为 `yyyy-MM-dd HH:mm:ss` 和 `yyyy-MM-dd`；
  - 部门结果 `nullResult` 视为失败，人员结果 `nullResult` 视为空；
  - 数组中的 null 元素跳过；
  - `HrmClientException` 转为 `ServiceException`，使用客户端已脱敏的说明。
- 与来源无关的快照校验放在通用层：重复 ID、缺少父级、出现环、跨分部记录、ID 格式。
- 构建者可按实际代码判断某项校验属于哪一层；判断标准是：换一个来源后，这项规则是否仍然成立。

### 6.4 `none` 模式与来源获取

- 同步服务和绑定校验注入 `ObjectProvider<OrgSyncSource>`，或注入一个统一的获取组件。没有实现时：
  - 部门同步、员工同步：**第一步**就抛出 `ServiceException("未启用组织信息来源，无法同步")`，不读取部门、不加锁。
  - 部门新增/编辑：类型和业务 ID 改为**选填**。如果填了，仍校验格式、类型取值和身份唯一，但不调用外部校验；如果没填，按原有逻辑保存。
- `hrm` 模式（或今后任何已启用来源）下的部门表单（用户确认，**与 dev-bench 不同**）：
  - 类型和业务 ID **选填**。都不填时按普通本地部门保存，不调用外部来源，HRM 不可达也不影响；
  - 填了任一项，则两项都必须填写，并按 dev-bench `DeptHrmBindingValidator` 的完整规则校验（格式、身份唯一、调用来源确认存在、上级关系一致、重绑限制），外部调用失败则不保存；
  - 未绑定的部门不能发起部门同步，同步时后端提示「部门未完整配置组织来源绑定」；
  - dev-bench 中「新建部门必须配置类型和业务 ID」这一分支删除；其余对旧节点、重绑、移动的规则保留。
- 两种模式的差别只在于：填了绑定时，`none` 不调用外部确认存在，`hrm` 调用。
- 前端按钮不隐藏，点击后显示后端返回的提示（见第 9 节）。

## 8. 后端同步与接口

### 8.1 Entity / BO / VO / Mapper

- `SysDept`、`SysDeptVo`：增加 dev-bench 的全部部门 HRM 字段。
- `SysDeptBo`：只加 `deptType`、`businessId`，与 dev-bench 一致；`hrmSubcompanyId` 是否保留在 BO 中，以 dev-bench 实际用法为准，只读字段不接受前端写入。

- `SysDeptMapper`、`SysUserMapper` 及其 XML：搬入 dev-bench 新增的 HRM 方法，包括身份查询、行锁、批量快照更新、同名冲突、用户部门锁等。方法名可以去掉 `Hrm` 字样，改用通用命名，由构建者决定。
- 新增字段都必须写中文 JavaDoc（见 AGENTS.md）。

### 8.2 部门

- 接口：`POST /system/dept/{deptId}/sync-children`，权限 `system:dept:sync`，加 `@Log` 和 `@RepeatSubmit`，返回 `R<DeptSyncResultVo>`。
- 绑定校验：dev-bench `DeptHrmBindingValidator` 中的 `hrmClient` 调用换成 `OrgSyncSource`；`SysDeptServiceImpl` 在新增和修改时调用它，接入点与 dev-bench 相同。
- 同步编排：dev-bench `SysDeptHrmSyncServiceImpl` 中的 `parser.parse(hrmClient.getHrmDepartmentInfo(...))` 换成 `source.listDepartments(...)`，其余（锁、重算一次、planner、writer）保持不变。
- 规则：以 dev-bench 最新 `DeptHrmSyncPlanner`、`DeptHrmSyncWriter` 代码及其测试为准；部门规格第 4～9 节作为背景说明，与代码冲突处以代码为准。已知差异（`bdfe352`）：
  - 来源中**停用的部门连同整棵子树跳过**，不新增、不更新（快照父先子后，按父级是否已跳过逐层判断）；
  - 点击的普通部门在来源中已停用时，同步集合为空，仍算成功，只更新点击节点的成功时间；
  - `selectedCount` 含义为「排除停用节点及其子树后实际参与同步的后代数量」；
  - 前端结果展示按 dev-bench `bdfe352` 之后的 `admin-web/src/views/system/dept/index.vue` 文案。
  - 通用层用 `OrgDepartment.disabled` 判断跳过，不写 `"1".equals(canceled)`；`hrm_canceled` 仍写入原值。
  - 部门规格中针对停用节点的状态保护条目（例如新停用节点下有正常后代）在跳过逻辑下可能不再触发，移植时保留代码中仍存在的分支及测试，不另行补回规格中已被代码删除的行为。

### 8.3 员工

- 接口：`POST /system/user/{deptId}/sync`。dev-bench 为 `/sync-hrm`，这里去掉来源名，见第 12 节。权限 `system:user:sync`，加 `@Log` 和 `@RepeatSubmit`，返回 `R<UserHrmSyncResultVo>`。VO 可以改名为通用名，字段保持一致。
- 前置校验顺序：
  1. 来源已启用；
  2. 部门存在；
  3. 有该部门数据权限；
  4. 部门是普通部门；
  5. 已绑定业务 ID；
  6. 已配置初始密码。
- 其余规则：字段映射、第 6 节逐条处理规则、超级管理员保护、数据权限跳过、锁、缓存清理、返回结构，全部照 dev-bench 员工规格；与 dev-bench 最新 `UserHrmSyncPlanner`、`UserHrmSyncServiceImpl` 代码冲突时以代码为准（`bdfe352` 同时改了这两个类）。判断在职改为使用 `OrgEmployee.active`，`hrm_status` 写入 `rawStatus`。规格中「本地 `hrm_status='1'`」这一判断，改为「本地上次同步时为在职」：用当前来源把 `hrm_status` 原值翻译成在职与否，HRM 中即 `'1'`。翻译放在适配层提供的方法里，通用层不写 `'1'`。

## 12. 实现时自定的事项（请审阅）

以下事项不是你明确定下的，是我在设计里做的决定：

1. **由 `org-sync.source` 直接控制 common-hrm 是否加载**。之前讨论时我说过给 common-hrm 单独设一个 `hrm.enabled` 开关；现在改为直接读取 `org-sync.source`，避免两个开关不一致。common-hrm 只是读一个配置键，不依赖 system 的代码。
2. **员工同步接口改名为 `/system/user/{deptId}/sync`**（dev-bench 为 `/sync-hrm`）。部门同步接口 `/sync-children` 保持不变。表字段为了和 dev-bench 一致保留 `hrm_` 前缀，但接口名不涉及数据库，所以去掉了来源名。
3. **不做前端预检，部门同步按钮不禁用**，统一由后端提示（见第 9 节），以满足 `none` 模式下「按钮不隐藏、点击有提示」的要求。
4. **与来源无关的提示文案改为通用说法**，HRM 客户端的错误说明保持不变。
5. **`org-sync.source` 取值非法时启动失败**，不静默当作 `none`。
6. **`client-ip` 默认为空**；模板 prod 的 `log-response-body` 设为 `false`（dev-bench 当前为 `true`）。
7. 只改 MySQL 初始化脚本；不新增 `hrm:*:query` 菜单。

- 规格与代码冲突时以 dev-bench 最新代码为准，停用部门及子树跳过（第 2、8.2 节）；
